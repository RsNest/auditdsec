# auditdsec

Лёгкий агент на Go: читает Linux **auditd**, переводит сырые события на человеческий язык
и присылает их в **Telegram**. Для владельцев VPS/VDS, которым важна безопасность,
но не хочется разбираться в `type=SYSCALL arch=c000003e syscall=257`.

Вместо этого вы получаете в чат:

```
🚨 web01 · критично
Изменён файл SSH-ключей /root/.ssh/authorized_keys, пользователь uid=0
2026-10-09 20:14:03
          [🚫 Забанить 198.51.100.7]  [✅ Это я]
```

> **Статус: v0.2.** Работают разбор auditd, события, Telegram с кнопками, хранение,
> детектор брутфорса, блокировка адресов через nftables с эскалацией и защитой от
> самоблокировки, режим отладки, Docker. CrowdSec — v0.3 (см. [Дорожную карту](#дорожная-карта)).

## Что он замечает

| Событие | Тип | Важность |
|---|---|---|
| Вход по SSH | `ssh_login_ok` | под root — критично, иначе обычное |
| Неудачная попытка входа | `ssh_login_fail` | внимание |
| **Успешный вход после серии неудачных** | `login_after_bruteforce` | критично |
| Команда через sudo или su | `sudo` | обычное |
| Новый пользователь, смена пароля, правка sudoers | `user_change` | критично |
| Изменение `authorized_keys` | `authorized_keys_change` | критично |
| Правка cron, systemd-юнитов, `.bashrc` | `persistence` | внимание |
| Правка `sshd_config` | `config_change` | внимание |
| Чистка журналов, отключение аудита, загрузка модулей ядра | `log_tamper` | критично |
| Запуск программы из `/tmp`, `/dev/shm`, `/var/tmp` | `suspicious_exec` | внимание |
| Аудит остановлен или молчит | `auditd_stopped` | критично |

Два пункта выделю особо.

**Успешный вход после серии неудачных** — самый важный сигнал. Отдельно взятые неудачные
попытки это фон, который идёт на любом VPS круглосуточно. А вот если с того же адреса
сначала были десятки промахов, а потом вход удался, то пароль, скорее всего, подобрали.
Этого события нет в журнале аудита как такового: оно существует только как закономерность
между записями, и его находит детектор.

**Аудит остановлен** — тишина на взломанном сервере выглядит точно так же, как тишина
на спокойном, поэтому агент отдельно следит за тем, что журнал аудита вообще пишется,
и сообщает, если он пропал или не обновлялся слишком долго.

Любой тип можно разобрать подробно: `auditdsec explain authorized_keys_change`
или `/explain authorized_keys_change` в чате — что это значит, насколько опасно, что делать.

## Чего он не делает

Честный список на версию 0.2:

- **по умолчанию не банит, а только записывает.** Это не оплошность, а следствие
  безопасной установки: контейнер работает без единой capability и физически не может
  менять файрвол. Применение блокировок включается одной командой — см.
  [Блокировки](#блокировки). Агент при старте пишет в журнал предупреждение, если
  детектор включён, а применять блокировки некому.
- **не интегрируется с CrowdSec.** Настройки читаются, обмена с LAPI пока нет.
- **не различает вход по ключу и по паролю.** auditd этого прямо не пишет; надёжный
  способ — разбирать и журнал sshd, это в планах.
- **не защищает журнал от root.** Получивший root вычистит локальные логи. Поэтому
  критичные события сразу уходят в Telegram: это и есть копия вне хоста.

## Быстрый старт: Docker

Нужны Docker с Compose и работающий auditd на хосте (`systemctl status auditd`).

```bash
git clone https://github.com/RsNest/auditdsec.git
cd auditdsec

cp .env.example .env
nano .env                 # вписать AUDITDSEC_TG_TOKEN и AUDITDSEC_TG_CHAT_ID

docker compose up -d
docker compose logs -f
```

В чат придёт «auditdsec запущен на …» — значит токен и chat id верные.
Если сообщения нет, смотрите `docker compose logs auditdsec`: неверный токен или chat id
агент сообщает отдельной строкой `cannot reach Telegram`.
Дальше поставьте [правила аудита](#правила-аудита), иначе события по файлам
собираться не будут (входы по SSH и sudo работают и без них).

Контейнер монтирует `/var/log/audit` только на чтение, работает с `read_only: true`,
`cap_drop: ALL` и лимитом 64 МБ. Привилегии ему не нужны.

Имя хоста в сообщениях берётся из `/etc/hostname` хоста — compose монтирует его
специально для этого. Внутри контейнера своё имя хоста равно идентификатору контейнера,
и без этой подмены все алерты подписывались бы шестнадцатеричным кодом вместо имени
сервера. Переопределить можно через `AUDITDSEC_HOST`.

## Быстрый старт: бинарник

Если Docker не нужен:

```bash
make build
sudo make install                      # /usr/local/bin, /etc/auditdsec, systemd-юнит

sudo install -m 0600 /dev/stdin /etc/auditdsec/auditdsec.env <<'ENV'
AUDITDSEC_TG_TOKEN=123456789:AA...
AUDITDSEC_TG_CHAT_ID=111222333
ENV

sudo systemctl daemon-reload
sudo systemctl enable --now auditdsec
sudo systemctl status auditdsec
```

Бинарник статический, около 7 МБ, без зависимостей; в памяти занимает десятки мегабайт.

## Правила аудита

Входы по SSH, sudo и операции с учётными записями auditd пишет сам через PAM — правила
для них не нужны. А вот слежение за файлами нужно включить:

```bash
sudo make rules          # копирует правила, добавляет .ssh всех пользователей, перезагружает auditd
```

Или вручную:

```bash
sudo cp deploy/auditdsec.rules /etc/audit/rules.d/50-auditdsec.rules
sudo deploy/gen-sshkeys-rules.sh | sudo tee -a /etc/audit/rules.d/50-auditdsec.rules
sudo augenrules --load
auditdsec check-rules        # every key the agent acts on must be listed as present
sudo auditctl -l | head
```

`gen-sshkeys-rules.sh` нужен потому, что в правилах аудита нельзя написать `/home/*/.ssh`:
маски не поддерживаются, и строка требуется на каждый домашний каталог. После добавления
пользователя скрипт стоит запустить снова.

Имена ключей (`-k ads_identity` и остальные) должны совпадать с теми, что ждёт агент.
Если переименовать ключ в правилах, агент перестанет понимать событие.

Проверить, что всё сошлось:

```bash
sudo touch /etc/passwd            # должно прийти сообщение об изменении учётных записей
```

## Блокировки

Детектор считает неудачные входы по каждому адресу в скользящем окне. Когда счётчик
доходит до порога, адрес попадает в список блокировок, а при включённом применении —
и в файрвол.

### Эскалация, а не «навсегда с первого раза»

| Нарушение | Срок |
|---|---|
| первое | 1 час |
| второе | 1 сутки |
| третье | 30 суток |
| четвёртое и далее | навсегда |

Так сделано намеренно. Адреса переиспользуются: NAT оператора, офисный шлюз, телефон,
сменивший сеть. Блокировка навсегда с первой ошибки означала бы, что агент вредит
владельцу сильнее, чем атака, поэтому «навсегда» достаётся только тому, кто возвращается.

### Защита от самоблокировки

Три независимых barrier, чтобы агент не выставил владельца за дверь:

1. **Белый список сильнее бана.** Проверка стоит в самом хранилище, поэтому обойти её
   не может ни детектор, ни кнопка в чате. Добавление в белый список снимает
   существующую блокировку — и в файрволе тоже.
2. **Белый список первого входа — по выбору.** `ban.auto_allowlist: first_login` заносит
   в белый список адрес первого успешного входа после запуска. Для новых установок
   по умолчанию `off` (первый вход не обязательно ваш); явная настройка сохраняется.
3. **Loopback, link-local и multicast не блокируются никогда; частные сети (`10.*`, `192.168.*`) — только при `ban.ban_private: true`.**

Плюс кнопка **✅ Это я** под каждым алертом: она снимает блокировку и заносит адрес
в белый список одним нажатием.

### Как включить применение блокировок

По умолчанию `ban.backend: none` — решения записываются и приходят в чат, но файрвол
не меняется. Это честный компромисс: контейнер из `docker-compose.yml` работает с
`cap_drop: ALL` и не может трогать netfilter.

Включение для Docker — отдельный override-файл:

```bash
docker compose -f docker-compose.yml -f deploy/compose.enforce.yml up -d --build
```

Он делает три вещи, и каждая обязательна: берёт образ с целью `enforce` (в нём есть
`nft`, которого нет в образе на `scratch`), даёт `NET_ADMIN` и переводит контейнер
в сетевое пространство хоста, иначе правила не влияли бы на его трафик.

Для установки бинарником достаточно указать backend — агент уже работает как root:

```yaml
ban:
  backend: nftables
```

Сначала можно посмотреть, что будет происходить, ничего не меняя:

```yaml
ban:
  dry_run: true     # в журнал пишется точная команда nft, файрвол не трогается
```

### Что именно создаётся в файрволе

Всё живёт в собственной таблице `inet auditdsec`, поэтому ufw, firewalld и цепочки
Docker не затрагиваются:

```bash
nft list table inet auditdsec     # посмотреть
nft delete table inet auditdsec   # удалить всё, что сделал агент
```

Таблица пересоздаётся при каждом запуске, а активные блокировки заново накладываются
из хранилища. Источник истины — хранилище, а не то, что осталось в файрволе после
перезагрузки.

### Чего детектор не делает

Решения по записям старше их собственного окна не применяются. Если при первом запуске
включить `read_from_start: true` на сервере с готовым журналом, агент разберёт историю,
покажет события, но не станет блокировать адреса за атаки, которые закончились неделю
назад.

## Телеграм-бот

Telegram можно подключить после установки: **Оповещения → Настроить Telegram**.
В форме задаются токен, user ID / chat ID получателей (до 16), категории событий,
уведомления о блокировках и запуске, порог важности, тихие часы и лимит сообщений.
«Проверить бота» проверяет токен без отправки; «Отправить тест» отправляет сообщение
всем указанным получателям. «Сохранить» применяет настройки без перезапуска.
Пустое поле токена сохраняет прежний секрет; галочка отключения Telegram сохраняет
настройки, но прекращает уведомления и команды. Токен не возвращается в браузер.

Настройки хранятся в `state/telegram-settings.json` с правами `0600` и имеют приоритет
над `.env` и YAML. Сохранение атомарное; ошибка проверки бота или записи оставляет
прежние настройки активными. Повреждение файла отключает Telegram с объяснением
в панели. Агент продолжает собирать события, даже если бот ещё не настроен.

Создайте бота у [@BotFather](https://t.me/BotFather), получите токен. Затем напишите
боту любое сообщение и узнайте свой chat id:

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" | grep -o '"chat":{"id":[-0-9]*'
```

Бот отвечает **только** чатам из `chat_ids`. Указывайте доверенные чаты: список
получателей также разрешает выполнять команды бота. Без токена или списка
получателей Telegram не запускается; сам агент и панель продолжают работать.

| Команда | Что делает |
|---|---|
| `/status` | хост, профиль, время работы, события за 24 ч, состояние оповещений |
| `/last [N]` | последние события, свежие сверху |
| `/allow <IP>` | добавить адрес в белый список (его нельзя забанить) |
| `/unallow <IP>` | убрать из белого списка |
| `/allowlist` | показать белый список |
| `/ban <IP>` | заблокировать адрес вручную |
| `/bans` | список блокировок; ✓ означает «применена в файрволе» |
| `/unban <IP>` | снять блокировку |
| `/mute [часы]` | заглушить оповещения (критичные всё равно придут) |
| `/unmute` | включить оповещения |
| `/explain <тип>` | объяснить тип события |
| `/debug` | диагностика: состояние агента и как включить отладку |
| `/help` | список команд |

Под алертами есть кнопки: **🚫 Забанить**, **✅ Это я** (адрес уходит в белый список)
и **🔕 Тишина 24 ч**.

## Веб-панель

То же, что показывает бот, только в браузере: состояние, лента событий с фильтрами,
баны и доверенные адреса, оповещения, диагностика. Бот будит вас ночью, панель
отвечает на вопрос «что вообще происходило».

Сам агент порт наружу не открывает: панель публикует только `./install.sh`, когда вы
это выбрали. Агент слушает обычный HTTP на `127.0.0.1` (upstream), а наружу смотрит
обратный прокси Caddy с доверенным HTTPS-сертификатом на выбранном вами порту.

### Установка

```sh
./install.sh
```

Один продукт, одна панель: выбора «новичок / профессионал» нет. Порядок вопросов
фиксирован:
0. **Язык установщика** — русский по умолчанию или English. Это первый вопрос,
   до проверок и скачивания образов. Выбор сохраняется в `PANEL_INSTALLER_LANG`
   при записи конфигурации; повторный запуск использует его без вопроса.
   `./install.sh --lang en` или `--lang ru` явно меняет язык. Без терминала
   используется сохранённый язык, а на новой установке — русский.
   Язык Telegram и UI этим выбором не меняется. Коды ошибок, команды и `Link:`
   остаются машинно читаемыми; вывод Docker, curl и certbot остаётся исходным.

1. **Preflight** — Linux amd64/arm64, Docker с Compose, curl, прежняя установка (её данные,
   сертификаты и учётные данные сохраняются). Здесь же скачивается образ агента: проверки
   ниже выполняются внутри него.
2. **Где открыть панель** — на **домене** или на **публичном IP** сервера.
3. **Проверка адреса.** Домен: публичные A и AAAA с нескольких независимых DNS-серверов,
   CNAME разворачивается; каждая запись должна вести на этот сервер — лишняя A или
   ошибочная AAAA останавливают установку (`dns_mismatch`) с перечнем найденного и
   ожидаемого. IP: установщик предлагает найденные адреса; если их несколько — просит
   выбрать. За NAT адрес задаётся `--public-ip`.
4. **Порт панели** — подобрать автоматически (сначала 443, затем до 16 случайных портов
   из 20000–29999) или указать вручную. Указанный вами порт никогда не подменяется: не
   подошёл — установка останавливается. Для каждого кандидата: можно ли занять порт на
   этом сервере (IPv4 и IPv6), затем временный слушатель с одноразовым значением и
   **проверка снаружи** через RemoteProbe (см. ниже).
5. **Что нужно сертификату.** Сертификат привязан к имени или адресу, не к порту, но
   подтверждение у Let's Encrypt приходит только на **80** (HTTP-01) или **443**
   (TLS-ALPN-01). Для IP нужен порт 80 снаружи. Для домена — 80, либо 443, если панель
   сама на 443. Открытый порт 27431 выпуску не помогает (`acme_challenge_unreachable`).
   Затем e-mail для Let's Encrypt и, если их ещё нет, токен и chat id бота (токен
   вводится без эха).
6. **Запуск и итоговая проверка снаружи** — уже по HTTPS с проверкой сертификата.
7. **Итог.** Ссылка — последней строкой и с настоящим портом (`:443` опускается):

```
  First login:  admin / admin
                It opens only the mandatory setup screen: ...
  Link: https://203.0.113.10:27431
```

«Published» печатается только когда прошла проверка снаружи с production-сертификатом.
`--staging`, `--no-start`, `--no-verify`, `--no-external-check`, `--mode selfsigned` и
туннель — технические режимы: итог прямо пишет, что панель **не опубликована**.

Без вопросов:

```sh
./install.sh --yes --mode domain --site panel.example.com --email you@example.com \
             --probe-url https://probe.example.net:8443 --probe-token-file /root/probe.token
./install.sh --yes --mode ip --site 203.0.113.10 --https-port 27431 \
             --probe-url https://probe.example.net:8443 --probe-token-file /root/probe.token
```

`--port` — старое имя `--upstream-port`: это всегда был порт агента на loopback, а не
публичный. В `.env` он теперь называется `PANEL_UPSTREAM_PORT` (старый `PANEL_PORT`
переносится при повторном запуске), публичный — `PANEL_HTTPS_PORT`, ссылка —
`PANEL_PUBLIC_URL`. Полный список флагов и кодов выхода: `./install.sh --help`.

### Проверка снаружи (RemoteProbe)

`curl` с самого сервера, даже на собственный публичный адрес, ничего не доказывает:
файрвол провайдера, security group и NAT видны только извне. Поэтому установщик просит
**другую машину** подключиться к выбранным адресу и порту. Это
`cmd/auditdsec-probe` — небольшой сервис, который вы запускаете сами на отдельном узле
(другой VPS, домашний сервер). Готового публичного сервиса нет и не подразумевается;
никакие секреты сторонним «проверялкам портов» не отправляются.

```sh
go build -o auditdsec-probe ./cmd/auditdsec-probe       # на другой машине
./auditdsec-probe -generate-token > probe.token
./auditdsec-probe -listen :8443 -cert fullchain.pem -key privkey.pem -token-file probe.token
```

Сервис не превращается в сканер: только по токену, лимит частоты (общий и на адрес) и
числа одновременных проверок, отказ для private/loopback/link-local/metadata-адресов
(проверяется и перед соединением, и на самом сокете), имя хоста принимается, только если
оно разрешается в тот же адрес (защита от DNS rebinding), соединение — к литералу адреса,
редиректы не выполняются. Без `-cert` он слушает только loopback.

Результаты: `reachable`, `refused`, `timeout`, `wrong_endpoint`, `unknown`. `timeout` не
называет причину: это может быть локальный файрвол, файрвол провайдера, NAT или маршрут.
Нет провайдера — это `external_check_unavailable`, а не «порт закрыт». Контракт — в
[docs/PANEL.md](docs/PANEL.md#контракт-remoteprobe).

### Коды ошибок

| Код | Выход | Что значит |
|---|---|---|
| `port_in_use` | 10 | порт занят на этом сервере (показано, кем, если `ss` это знает); чужой процесс не останавливается |
| `external_port_unreachable` | 11 | порт свободен здесь, но снаружи не достижим |
| `external_check_unavailable` | 12 | нет RemoteProbe или он не ответил; про порт это ничего не говорит |
| `dns_mismatch` | 13 | публичный DNS ведёт не только на этот сервер |
| `acme_challenge_unreachable` | 14 | 80 (или 443) недоступен для подтверждения, либо 80 занят другим веб-сервером |
| `certificate_issuance_failed` | 15 | CA не выдал сертификат |
| `tls_validation_failed` | 16 | сертификат панели не проверяется |
| `service_start_failed` | 17 | контейнеры не поднялись или страница не отвечает |
| `bootstrap_persistence_failed` | 18 | панель не может сохранить учётные данные |

В каждой ошибке — адрес и порт, что проверялось, результат (или честное «неизвестно»),
что исправить и точная команда повтора. Ни токен, ни пароль в выводе не появляются.
Установщик не отключает файрвол и не добавляет правил: при блокировке он говорит, какой
порт открыть. В автоматическом режиме он переходит к следующему порту, только если
ошибка касается именно порта; сбой DNS или RemoteProbe останавливает подбор. Если не
подошёл ни один кандидат, итог перечисляет проверенные порты и причины — и не утверждает,
что «закрыты все порты».

### Первый вход: admin / admin и обязательная смена

На новой установке первый вход — **`admin` / `admin`**. Эта пара открывает только
короткую сессию настройки: до смены учётных данных сервер отказывает во всех остальных
запросах (события, диагностика, настройки, баны, экспорт), обойти экран через URL, API,
обновление страницы или повторный вход нельзя.

На экране настройки: новый логин (оставить `admin` можно, только отметив «Точно оставить
логин admin»), пароль дважды — минимум 8 символов, строчная и заглавная буква; индикатор
надёжности и кнопка «показать». Все правила проверяет сервер. Новые данные пишутся
атомарно, только хешем (PBKDF2-SHA256), в `panel-credentials.json` (права 0600, том
состояния); после этого `admin` / `admin` больше не работает, сессия настройки
отзывается. Перезапуск, обновление и повторный `./install.sh` их не сбрасывают.

Пока настройка не завершена, тот, кто откроет ссылку первым, может выбрать логин и пароль
сам — заходите сразу. Если состояние нельзя записать, панель сообщает `locked`, а
установщик — `bootstrap_persistence_failed`: экран настройки, результат которого
потеряется, не предлагается. Восстановить доступ можно только локально:
`auditdsec reset-credentials -yes` на сервере. `--password-file` задаёт пароль сразу,
без экрана настройки.

### Пробный запуск (staging) и переход на production

У Let's Encrypt есть тестовый CA — staging: шаги те же, лимиты выше, сертификат браузеры
не принимают. Включается только явно:

```sh
./install.sh --mode domain --site panel.example.com --email you@example.com --staging
./install.sh --production           # тот же сервер, те же данные, настоящий CA
```

Состояние staging и production разделено (отдельные тома с суффиксом `-staging`),
ничего не удаляется, агент, события и пароль не затрагиваются. Staging никогда не
называется опубликованной панелью. Успешный staging не доказывает, что production
выдаст сертификат именно этому имени или адресу.

### Куда установщик отправляет пароль

Проверка входа (`admin` / `admin` или пароль из `--password-file`) идёт **только по
соединению, чей сертификат проверен**: по системному хранилищу, по `--cacert` либо по
корню собственного CA прокси. Иначе — на `127.0.0.1` агента на этом же сервере.

### Если что-то пошло не так

- Пока ничего не запущено (DNS, порт, проверка снаружи, порт подтверждения), установщик
  ничего не меняет: временный слушатель удаляется, собственный прокси прежней установки,
  остановленный на время проверки портов, запускается снова.
- После успешной проверки копия настроек хранится в `.env.last-good` (0600). Если новая
  конфигурация не поднялась, установщик сам возвращает её; неудачная лежит в `.env.failed`,
  тома и сертификаты не тронуты. Вручную: `./install.sh --restore`.
- Посторонний веб-сервер на порту 80 установщик не останавливает и подтверждение через
  него не маршрутизирует: это ошибка `acme_challenge_unreachable` с объяснением.
  DNS-01 пока не поддерживается.

### Сертификат на IP-адрес

Let's Encrypt выдаёт сертификаты на публичные IPv4 и IPv6 (см.
[анонс](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)), только по профилю
`shortlived` — около 6 дней, и только с подтверждением HTTP-01 на порту 80: DNS-01 к
адресу неприменим. Выпускает и продлевает закреплённый certbot (`certbot/certbot:v5.8.0`,
меняется `CERTBOT_IMAGE`; `--ip-address` есть начиная с 5.3).

1. Перед использованием сертификата проверяются SAN, срок, окружение и ACME-сервер,
   соответствие ключа; наличие файла ничего не доказывает.
2. Цикл в контейнере certbot раз в 12 часов вызывает `certbot renew` (повтор через час) и
   раз в минуту сверяет файл на диске с тем, что реально отдаёт порт панели.
3. Перезагрузка Caddy не считается удавшейся, пока отпечаток на порту панели не совпал с
   новым файлом; иначе контейнер certbot становится `unhealthy`.
4. Смена адреса — новый сертификат, старый остаётся в архиве certbot.

Порт 80 должен оставаться открытым и свободным. Лимит production — 5 сертификатов на
адрес за 168 часов. Состояние: `docker compose exec certbot python3 /hooks/certtool.py status`.

**Наблюдение агента.** Независимо от способа выпуска агент раз в час подключается к
своей ссылке и смотрит сертификат, который прокси реально отдаёт: истёк, осталось меньше
четверти срока (продление уже должно было пройти) или не проверяется по системным CA.
Проблема приходит в Telegram как `panel_cert` (не чаще раза в 6 часов) и видна в `/debug`
и `/api/v1/diagnostics` (`panel_cert`). Для staging, самоподписанного и `--cacert`
установщик включает режим `expiry`: только срок. Настройка — `web.cert_check`
(`verify`, `expiry`, `off`).

### Режимы для разработки: туннель и самоподписанный

`--mode tunnel` (панель на `127.0.0.1:9477`, доступ через `ssh -L`) и `--mode selfsigned`
(Caddy `tls internal`, браузер предупреждает) остались для совместимости и разработки.
Они включаются только явным флагом, никогда — как запасной вариант при неудачной
публикации, и итог не называет их опубликованной панелью.

### Файлы развёртывания

| Файл | Назначение |
|---|---|
| `docker-compose.yml` | агент |
| `deploy/compose.proxy.yml` | Caddy перед панелью: `PANEL_SITE`, `PANEL_HTTPS_PORT`, `PANEL_UPSTREAM_PORT` |
| `deploy/compose.acme-ip.yml` | certbot для IP-сертификата (образ закреплён, staging и production в разных томах) |
| `deploy/certtool.py`, `certbot-loop.sh`, `certbot-deploy-hook.sh` | проверка сертификата, продление, перезагрузка Caddy с проверкой отпечатка |
| `deploy/Caddyfile`, `.acme-ip`, `.selfsigned` | конфигурации Caddy; выбирает `PANEL_CADDYFILE`. HTTP/3 выключен (UDP не нужен), admin API Caddy только на `127.0.0.1:2019` |
| `deploy/compose.tunnel.yml` | панель на loopback хоста (режим разработки) |
| `deploy/compose.enforce.yml` | применение блокировок в nftables |
| `cmd/auditdsec-probe` | RemoteProbe для запуска на другой машине |

Диагностика:

```sh
docker compose logs auditdsec | head        # public_url и состояние настройки
docker compose ps
docker compose logs caddy certbot
```

Что проверено на стенде, а что нет — [docs/VERIFY.md](docs/VERIFY.md).

### Что защищает панель

- **Пароль хранится хешем** (PBKDF2-SHA256, 310 000 итераций), сравнение — за время,
  не зависящее от значения. Неверное имя пользователя стоит столько же, сколько неверный
  пароль: иначе имя можно было бы подобрать по секундомеру.
- **Лимит попыток входа:** 5 неудач с одного адреса за 10 минут — и адрес ждёт. Удачный
  вход счётчик обнуляет. Каждая неудача и каждый вход попадают в журнал агента.
- **Токен сессии** случайный, 256 бит, живёт 12 часов и хранится в памяти только хешем.
  Перезапуск агента завершает все сессии.
- **Подделать адрес клиента нельзя:** `X-Forwarded-For` принимается только от
  перечисленных в `web.trusted_proxies`, иначе берётся адрес сокета.
- **CSRF:** изменяющие запросы требуют заголовок `X-Requested-With`, запросы с чужого
  Origin отклоняются. Токен не лежит в cookie, поэтому браузер не подставит его сам.
- **Строгий CSP:** ни одного встроенного скрипта или стиля, ни одного внешнего адреса.
  Значения из журнала аудита попадают на страницу только как текст.
- **Свой адрес не забанить** через панель: попытка заблокировать адрес, с которого вы
  пришли, отклоняется — иначе одним щелчком можно отрезать себя от сервера.
- **Публичный адрес и `0.0.0.0` в `web.listen` агент не примет.** Панель живёт за обратным прокси
  или в туннеле, а не отвечает незнакомцам по открытому HTTP.

Подробности контракта API и описание страницы — в [docs/PANEL.md](docs/PANEL.md).

## Настройки

Всё настраивается файлом (`config.example.yaml` — шаблон с комментариями) или
переменными окружения; переменные важнее файла, поэтому секреты держите в них.

| Переменная | Значение |
|---|---|
| `AUDITDSEC_TG_TOKEN` | токен бота |
| `AUDITDSEC_TG_CHAT_ID` | разрешённые chat id через запятую |
| `AUDITDSEC_PROFILE` | `simple` или `pro` |
| `AUDITDSEC_LANG` | `ru` или `en` |
| `AUDITDSEC_HOST` | имя хоста в сообщениях |
| `AUDITDSEC_AUDIT_LOG` | путь к `audit.log` |
| `AUDITDSEC_STATE_DIR` | каталог состояния |
| `AUDITDSEC_CONFIG` | путь к файлу настроек |
| `AUDITDSEC_BAN_BACKEND` | `none` или `nftables` |
| `AUDITDSEC_BAN_DRY_RUN` | `1` — только показывать команды, ничего не блокировать |
| `AUDITDSEC_AUTO_ALLOWLIST` | `off` (по умолчанию для новых установок) или `first_login` |
| `AUDITDSEC_BAN_PRIVATE` | `true` — разрешить баны частных сетей (по умолчанию нет) |
| `AUDITDSEC_DEBUG` | `1` — включить [режим отладки](#режим-отладки) |
| `AUDITDSEC_LOG_FILE`, `AUDITDSEC_LOG_LEVEL` | свой журнал агента |
| `AUDITDSEC_MIN_SEVERITY` | порог алертов: `info`, `warn`, `critical` |
| `AUDITDSEC_RETENTION_DAYS` | срок хранения событий |
| `AUDITDSEC_WEB_UPSTREAM_LISTEN` (старое `AUDITDSEC_WEB_LISTEN`) | адрес агента для прокси, только loopback |
| `AUDITDSEC_WEB_PUBLIC_HTTPS_PORT` | публичный HTTPS-порт панели (для ссылки и проверки) |
| `AUDITDSEC_WEB_PUBLIC_URL` | ссылка на панель с настоящим портом |

Проверить настройки перед запуском (токен в выводе маскируется):

```bash
auditdsec check-config -config /etc/auditdsec/auditdsec.yaml
```

Полезные параметры файла:

- `min_severity` — порог отправки. События ниже порога всё равно пишутся на диск и видны в `/last`.
- `dedup_window` — окно склейки повторов: одинаковые события внутри окна становятся
  одним сообщением и счётчиком «ещё N».
- `quiet_from` / `quiet_to` — тихие часы для некритичного.
- `rate_per_minute` — предохранитель от шторма сообщений.
- `heartbeat.stale_after` — через сколько молчания журнала считать аудит мёртвым.
- `read_from_start` — читать ли существующий журнал при первом запуске (по умолчанию нет,
  чтобы установка не вылилась в чат историей за месяцы).

## Профили simple и pro

| | simple | pro |
|---|---|---|
| Для кого | один VPS, не админ | 5–10 серверов |
| Порог алертов | `warn` (sudo пишется, но не шлётся) | `info` (всё) |
| Хранение | 14 дней | 90 дней |
| Лимит сообщений | 10/мин | 30/мин |
| Окно склейки | 10 минут | 5 минут |
| Heartbeat | 6 часов | 2 часа |
| Порог брутфорса | 10 за 10 минут | 5 за 5 минут |

Профиль — это набор значений по умолчанию, любое из них можно переопределить. **Профили
устаревают как выбор**: продукт один, сборка одна. `profile: simple|pro` в старых
файлах по-прежнему читается как пресет начальных значений, явно заданные ключи важнее
него; установщик о профиле не спрашивает. Номер версии релиза (`auditdsec version`) от
профиля и набора включённых функций не зависит.

## Режим отладки

Отладка включается **отдельно** и отвечает на главный вопрос, который возникает при
настройке: *почему алерт не пришёл*. По умолчанию выключена.

### Как включить

Три способа, любой на выбор. Каждый следующий важнее предыдущего.

| Способ | Как | Когда удобнее |
|---|---|---|
| Переменная окружения | `AUDITDSEC_DEBUG=1` | Docker: вписать в `.env` и `docker compose up -d` |
| Файл настроек | `debug: true` | когда агент уже настроен файлом |
| Флаг командной строки | `auditdsec run -debug` | разовый запуск руками |

```bash
# Docker
echo 'AUDITDSEC_DEBUG=1' >> .env
docker compose up -d
docker compose logs -f auditdsec

# systemd
sudo systemctl edit auditdsec     # [Service] / Environment=AUDITDSEC_DEBUG=1
sudo systemctl restart auditdsec
sudo journalctl -u auditdsec -f

# вручную
auditdsec run -config /etc/auditdsec/auditdsec.yaml -debug
```

Проверить, включена ли отладка, можно двумя способами: `auditdsec check-config` покажет
строку `debug: true`, а команда **`/debug`** в чате выведет состояние агента и напомнит,
как отладку включать и выключать.

### Как выключить

Убрать переменную, `debug: true` или флаг — и перезапустить агента. Отладка никогда
не остаётся включённой «сама»: состояние берётся только из этих трёх источников.

### Что появляется в журнале

Уровень журнала поднимается до `debug` автоматически — отдельно его менять не нужно.
В журнал агента (`log.file`, по умолчанию `/var/log/auditdsec/auditdsec.log`, в Docker —
`/var/lib/auditdsec/auditdsec.log` плюс `docker compose logs`) добавляется:

- **каждая прочитанная строка** `audit.log`;
- **причина, по которой запись отброшена** — самое полезное. Например, опечатка
  в ключе правила видна сразу:

  ```json
  {"level":"DEBUG","msg":"audit event ignored","types":"SYSCALL","serial":2,
   "keys":"my_own_typo",
   "reason":"no rule for audit key \"my_own_typo\" (keys the agent knows: ads_exec_tmp,
             ads_identity, ads_logs, ads_modules, ads_persist, ads_sshd, ads_sshkeys, ads_sudoers)"}
  ```

- **решение по каждому алерту** — отправлен, склеен с повторами, задержан порогом,
  тишиной или mute:

  ```json
  {"level":"DEBUG","msg":"alert decision","verdict":"held","kind":"sudo",
   "severity":"info","reason":"severity info is below min_severity=warn"}
  {"level":"DEBUG","msg":"alert decision","verdict":"grouped","kind":"ssh_login_fail",
   "ip":"198.51.100.7","reason":"repeat 12 inside the 10m dedup window"}
  ```

- **счётчики раз в 30 секунд**, чтобы отличить спокойного агента от зависшего.

### Секреты и в отладке остаются скрытыми

Сырые строки проходят через ту же маскировку. auditd хранит команду в hex, поэтому агент
декодирует её, маскирует и подставляет обратно в читаемом виде:

```
cmd=6D7973716C202D7068756E74657232   →   cmd="mysql -p***"
```

Если бы hex писался в журнал как есть, пароль утёк бы в файл в обратимом виде.
Токен бота в журнал не попадает ни в каком режиме.

Отладку стоит выключать после настройки: в журнал идёт каждая строка `audit.log`,
на шумном сервере это заметный объём (ротация ограничивает файл, но место под ротацию
всё равно расходуется).

## Как это устроено

```
audit.log → source → parse → semantic → ┬→ store (JSONL по дням)
          (поллинг)  (склейка  (смысл и  └→ notify (Telegram)
                     событий)  важность)
```

- **source** следит за файлом поллингом раз в секунду, понимает ротацию и усечение,
  запоминает смещение, так что перезапуск не теряет и не дублирует события.
- **parse** собирает записи одного события по серийному номеру и раскрывает
  вложенный `msg='...'` и hex-значения, которыми auditd кодирует команды.
- **semantic** переводит это в событие с типом, важностью, пользователем и адресом.
- **store** пишет по файлу JSONL на сутки — ретеншн сводится к удалению старых файлов,
  а сами события остаются читаемыми обычным `grep` и `jq`.
- **notify** применяет политику: порог, mute, тихие часы, склейку повторов, лимит.

Внешних зависимостей нет: только стандартная библиотека Go. Подробнее —
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Безопасность

- **Секреты маскируются.** Пароли и токены в командах заменяются на `***` — и в сообщении,
  и в том, что ложится на диск. auditd кодирует команду в hex, поэтому агент декодирует
  её, маскирует и подменяет hex в сохранённой копии: иначе пароль утекал бы в файл в
  обратимом виде.
- **Токен не попадает в логи.** Он есть только в URL запроса, и из текстов ошибок
  вырезается.
- **Белый список сильнее бана.** Адрес из белого списка забанить нельзя — это защита
  от самоблокировки на динамическом адресе. Добавление в белый список снимает
  существующий бан.
- **Контейнеру не нужны привилегии.** Только чтение `/var/log/audit`, `cap_drop: ALL`,
  `read_only`. Применение блокировок требует `NET_ADMIN` и включается отдельным
  override-файлом: агент не должен уметь трогать файрвол по умолчанию.
- **Панель не открывается посторонним по открытому HTTP.** Агент слушает только loopback,
  наружу — Caddy с TLS. Пароль хранится хешем, попытки входа ограничены, сессии живут в
  памяти; первая пара `admin` / `admin` открывает только экран обязательной настройки.
  Подробнее в разделе [Веб-панель](#веб-панель).
- **Входящее из чата не доверяется.** Команды принимаются только от разрешённых chat id,
  а значения из журналов экранируются перед отправкой, чтобы путь к файлу не мог
  подделать разметку сообщения.

- **Этап 0 — сделано в ветке.** Публикация панели на домене или публичном IP на

  ошибок установщика, обязательная первая настройка `admin` / `admin`.

  идентичностью файла, устойчивая очередь доставки, корреляция брутфорса после бана,
  маскирование всех представлений команд, единый сервис решений. См.

  командами исправления, режим обучения на 3–7 дней и алерты на новое поведение,
  второй backend блокировок (ipset) для хостов на iptables.
- **v0.4.** Профиль pro: несколько хостов в одном чате, метрики Prometheus,
  маршрутизация оповещений (ntfy, webhook, Discord), `auditdsec query`.

## Разработка

```bash
make check      # gofmt, go vet, go test
make build      # bin/auditdsec
make docker     # образ
go test ./internal/parse/ -run TestParseLine -v
```

Требуется только Go 1.24, зависимостей нет. Тесты разбора написаны на настоящих строках
`audit.log`, Telegram проверяется через `httptest` без сети.

## English

**auditdsec** is a lightweight Go agent that reads the Linux audit log, explains what
happens on a host in plain language and reports it to Telegram. It is aimed at VPS owners
who care about security without wanting to read raw auditd records.

It reports SSH logins, failed login attempts, sudo commands, account and sudoers changes,
`authorized_keys` edits, persistence (cron, systemd, shell profiles), `sshd_config`
changes, log and audit tampering, execution from temporary directories — and, importantly,
auditd going silent, because silence on a compromised host looks just like silence on a
quiet one.

v0.2 ships parsing, alerting with inline buttons, bot commands, a sliding-window
brute-force detector, nftables bans with escalation (1h → 1d → 30d → permanent) and a
dry-run mode, three independent safeguards against banning its own owner, storage with
retention, the heartbeat, a debug mode, Russian and English, Docker and systemd.
Enforcement is off by default because the default container holds no capabilities;
`deploy/compose.enforce.yml` turns it on. CrowdSec is v0.3.

Quick start, configuration, the bot command list and the security notes are in the Russian
sections above; the settings themselves are documented in English in
[`config.example.yaml`](config.example.yaml), and the design is described in
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md). Zero external dependencies: Go standard
library only.

### Durable alert delivery (stage 1.3)

Automatic Telegram notifications are journaled before delivery and sent by separate
routine/critical workers. Pending jobs, per-recipient retries, grouping counts and delivery
counters survive restart. The System panel shows pending, suppressed, grouped, deferred,
failed, cancelled and overflow counts. `alerts_sent` means provider acknowledgments per
recipient, not events passed to a notifier. Token changes and recipient removal cancel
stale jobs; queued messages are never rerouted to a replacement bot.

Keep `outbox/outbox.wal` and `.outbox.initialized` with the existing state volume when
updating. Missing or corrupt initialized outbox state stops startup. Do not remove the
marker to clear an error. Restore a matching state backup instead. See
[delivery guarantees and limits](docs/DELIVERY.md).
