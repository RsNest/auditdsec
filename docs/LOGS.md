# Логи и диагностика

Все компоненты auditdsec пишут диагностические логи в **один каталог на сервере**:
`/var/log/auditseclogs` (переменная `AUDITSEC_LOG_DIR`). Каждый компонент пишет в
**свой** файл: два процесса никогда не пишут в один файл.

| Файл | Кто пишет | Что внутри |
| --- | --- | --- |
| `installer.jsonl` | `install.sh` | этапы, проверки, ошибки и итог каждой операции |
| `installer-commands.log` | `install.sh` | сырой вывод программ, которые он запускал (`docker pull`, `compose up`) |
| `agent.jsonl` | агент | запуск, остановка, ошибки хранилища, проверок обновлений, паники |
| `api.jsonl` | API панели | неудачные, изменяющие и медленные запросы; паники |
| `frontend.jsonl` | панель в браузере | ошибки JavaScript, отклонённые промисы, сбои API и загрузки ресурсов |
| `control.jsonl` | `auditdsec-ctl` | задачи изменения доступа и стадии установщика |
| `caddy.jsonl` | Caddy | журнал запросов прокси (ротацию делает сам Caddy) |
| `certs.jsonl` | контейнер certbot | продления и сбои согласования сертификата для IP |

Каталог и файлы принадлежат root: каталог `0750`, файлы `0640`. Каталог не отдаётся
веб-сервером, браузеру и агенту не даётся ни доступ к файловой системе, ни Docker
socket. Права `777` не используются.

## Формат

Каждая запись — одна JSON-строка. Общие поля:

```json
{"ts":"2026-10-11T09:08:53.120Z","level":"error","service":"installer","event":"failure",
 "message":"dns_mismatch at panel.example.com: ...","version":"0.3.0","commit":"…",
 "trace_id":"4f1c…","operation":"change","error_code":"dns_mismatch"}
```

- `ts` — UTC с миллисекундами; `level` — `debug|info|warn|error`;
- `service` — компонент; `event` — машинное имя события;
- `trace_id` — идентификатор операции (см. ниже); `request_id` — идентификатор HTTP-запроса;
- `duration_ms`, `error_code` — когда применимо.

Секреты маскируются перед записью (`internal/redact` в Go, фильтр в `install.sh`):
пароли, токены, заголовки `Authorization`, пароли в URL, хеши паролей. Запись не
превышает ~3,5 КиБ (установщик) и обрезается с пометкой `[truncated]`.

## trace_id: как найти всё про одну операцию

Каждая операция установщика получает `trace_id`; он указан в итоге установки, в
сообщении об ошибке и (для изменений из панели) в задаче. Операция из панели несёт
один идентификатор через весь путь: **ID запроса панели → `control.jsonl` → переменная
`AUDITDSEC_TRACE_ID` установщика → `installer.jsonl`**. Ошибка браузера, связанная с
неудавшимся запросом, записывается с `trace_id` этого запроса.

```bash
sudo ./install.sh --logs                 # последние операции
sudo ./install.sh --logs TRACE_ID        # все записи операции из всех компонентов
sudo docker exec auditdsec auditdsec logs --trace TRACE_ID   # то же, из образа
```

Поиск читает только файлы (включая архивы и `.gz`), ограничен 5000 записями и 256 МиБ,
выводит записи по времени.

## Ротация и очистка

| Правило | Значение по умолчанию |
| --- | --- |
| размер активного файла | 10 МиБ |
| архивов на файл | 5 (`файл.1`, `файл.2.gz`, …; старше первого — gzip) |
| возраст архива | 14 дней |
| бюджет каталога | 512 МиБ |

Ротацию делает владелец файла: Go-компоненты — своим писателем, установщик — под
своим замком, Caddy — своими настройками `roll_*`. **Удаляет только архивы** — сначала
старше срока, затем самые старые, пока каталог не уложится в бюджет. Активные файлы,
файлы с другими именами и не-обычные файлы не удаляются. Настройки агента:
`log.dir`, `log.max_size_mb`, `log.max_backups`, `log.max_age_days`, `log.budget_mb`
в [config.example.yaml](../config.example.yaml).

Если файл удалён или заменён во время работы (logrotate, ручная очистка), писатель
замечает это и открывает новый.

## Если лог нельзя писать

Остановка из-за лога недопустима. Если каталог не примонтирован, нет места или нет
прав, компонент один раз пишет об этом в stderr, продолжает работать и сбрасывает записи;
когда запись снова возможна, сообщает об этом и сколько записей потеряно. Записи уровня
`error` и выше синхронизируются с диском сразу. Файл-маркер `agent.running` помогает
заметить аварийное завершение: при следующем запуске агент пишет `unclean_shutdown`.

## Ошибки браузера

Панель отправляет `POST /api/v1/client-log` только из открытой сессии, с тем же
заголовком `X-Requested-With`, что и любое изменение. Ограничения: тело до 8 КиБ,
сообщение 500, стек 2000 символов; из адресов страниц удаляются query и fragment;
время клиента не доверяется (в запись идёт время сервера, время клиента — как текст);
одинаковые ошибки не пишутся повторно 5 минут; не более 30 отчётов в минуту на сессию и
120 на всю панель. В браузере — короткая очередь (20), три попытки с растущими паузами,
после чего отчёт отбрасывается. Отчёты о сбое самой отправки не создаются.

## Что проверено

Проверено автоматически и воспроизводимо (`scripts/check-installer-ui.sh`,
`go test ./internal/logging ./internal/api ./internal/access`,
`node scripts/check-panel-review.cjs`): формат и маскирование, права файлов, ротация со
сжатием, переоткрытие файла, невозможность записи, очистка (только архивы, возраст,
бюджет), поиск по `trace_id` в нескольких потоках и архивах, ограничения и дедупликация
отчётов браузера, передача `trace_id` из панели в окружение установщика. Синтаксис
Caddyfile с новым журналом проверен настоящим `caddy adapt`.

**Не проверено на живом сервере:** запись в `/var/log/auditseclogs` внутри настоящих
контейнеров с привязкой каталога, ротация Caddy под нагрузкой и логи certbot при реальном
продлении. Эти части требуют установки на сервере.
